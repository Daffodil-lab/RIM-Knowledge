# 14. 最小データモデル

## 14.1 `ShionExpeditionProfileDef`

開始立場と初期工業状態をデータ駆動にする。

| フィールド候補 | 型 | α用途 |
|---|---|---|
| `defName` | DefName | 安定ID |
| `label` | 翻訳キー | 開始立場表示 |
| `description` | 翻訳キー | 開始説明 |
| `accountProfile` | v4 Account Profile参照 | 共同口座の生成規則 |
| `startingThings` | ThingDef＋数量のリスト | 五つの代表工業資源を含む初期物資 |
| `startingCurrencyBalance` | 64 bit整数 | 同盟通貨の初期残高 |
| `hasGuaranteedHomeSupport` | bool | 独立団ではfalse。表示と監査に使用 |
| `introTextKey` | string | 開始文 |
| `startingResearchTags` | stringリスト | 初期研究範囲の候補 |
| `bodyConfigurationProfile` | 身体構成Profile参照 | β。開始Pawnへ許可するPlatform、Module、外装の範囲 |
| `startingLoadoutProfile` | Loadout Profile参照 | β。具体装備と装備ファミリーの生成規則 |

α Def:

```text
Shion_IndependentExpeditionProfile
accountProfile = Shion_IndependentExpeditionAccount
hasGuaranteedHomeSupport = false
```

初期残高の数値はDefへ置き、本文へ固定しない。

## 14.2 `WorldComponent_ShionExpeditionState`

最低限、次を保存する。

| フィールド | 意味 |
|---|---|
| `dataVersion` | 同一ビルドのschema識別。α／βの版間移行は保証しない |
| `profile` | 使用中の`ShionExpeditionProfileDef` |
| `expeditionId` | セーブを跨ぐ一意ID |
| `kombinatAccountId` | v4で生成したKombinat共同口座 |
| `startingBalancesApplied` | 初期残高の重複適用防止 |

政治、幸福、団結、忠誠等を未使用の数値として先行保存しない。

## 14.3 `ScenPart_ShionExpeditionProfile`

責務:

1. 選択されたProfile DefをWorld状態へ登録する。
2. 一意の`expeditionId`を生成し、v4 Account作成境界から`kombinatAccountId`を受け取る。
3. 全ての開始資源Defと量を事前検証する。
4. v4の原子的なAccount取引境界で初期残高を一括適用する。
5. 全成功後に`startingBalancesApplied = true`とする。
6. 失敗時は適用済み加算をロールバックし、明瞭なエラーを表示する。

初期化中にフレームを跨がず、部分適用状態でセーブさせない。

## 14.4 Account ID

v4 Account作成境界で一度生成し、World状態へ保存する。文字列形式は実装fixtureで決め、旧`ownerId`形式を引き継がない。

- Pawn名を含めない。
- Map座標を含めない。
- 翻訳文字列を含めない。
- ロードごとに再生成しない。
- 将来Red Starへ変化しても、既存口座を黙って改名しない。

施設別口座が必要になった場合は、Kombinat仕様に従って追加する。

## 14.5 `ShionIndependentFactionProfileDef`（β）

独立勢力を単一のFactionDefへまとめないため、βでRimWorldの`FactionDef`から参照できる組織Profile境界を作る。国家級勢力とPMC型組織の完成コンテンツもβで追加する。

| フィールド候補 | 意味 |
|---|---|
| `organizationScale` | 数人、拠点網、都市連合、国家級等の生成規模 |
| `primaryFunctions` | 生活、研究、交易、救援、契約軍事・警備等 |
| `homeCommandRelation` | 本国の正規指揮へ属するか。独立Profileでは属さない |
| `guaranteedHomeSupport` | 本国保証支援の有無。独立Profileでは原則false |
| `governanceTags` | 統治・指揮の特徴。善悪の単一軸にしない |
| `logisticsProfile` | 自己保有する生産、補給、船団、拠点網 |
| `contractProfile` | 交易、雇用、護衛、救難、軍事契約の扱い |
| `aidAndForceProfile` | 救援規範、交戦姿勢、民間保護、撤収判断 |
| `worldGenerationProfile` | 拠点、キャラバン、サイト、来訪者の生成方法 |
| `relationProfile` | 他の独立勢力、本国、Red Star、現地派閥との初期関係 |

Profileは政治設定と生成規則をCore側で所有し、Kombinatには組織種別を判定させない。Kombinatは組織・拠点ごとのownerスコープと取引だけを扱う。

最初の派閥縦切りでは、少なくとも次の二Profileを共通基盤で成立させる。

1. 複数拠点と独自外交を持つ国家級独立勢力。
2. 契約、護衛、救難、戦闘を扱うPMC型組織。

双方を色違いの同一FactionDefにせず、支援源、行動理由、依頼、部隊生成、外交反応が異なることを確認する。固有名、国家制度、契約数値、装備カタログはProfile縦切り時に決める。

## 14.6 身体構成データ

本節の身体構成Runtimeはβで実装する。具体的なTierやスロット数より先に、責務の分離と同一ビルドの保存を成立させる。

| 境界 | 主なフィールド | 責務 |
|---|---|---|
| `ShionBodyPlatformDef` | 標準Interface、互換タグ、描画入口、保守方式 | 狐娘型の工業基盤 |
| `ShionBodyInterfaceDef` | 接続種別、許容条件、排他条件 | Module接続規格 |
| `ShionBodyModuleDef` | 必要Interface、効果、負荷、外装差分 | 交換・追加可能な機能 |
| `ShionBodyConfigurationProfileDef` | 許可Platform、必須／候補Module、調整・外装範囲 | 生成規則 |
| `ShionBodyConfiguration` | Platform、装着Module、個別調整、外装、履歴参照 | Pawnごとの保存正本 |

同一の`ShionBodyPlatformDef`から生成した二人でも、`ShionBodyConfiguration`は共有しない。Module交換時は、Interface、身体互換、競合、必要DLCまたはAdapterを検証してから状態を変更する。変更途中を保存正本にせず、失敗時は元の構成を保持する。

身体の品質、Module数、希少性を、Pawnの人格価値、権利、身分へ変換するフィールドは設けない。

## 14.7 `ShionLoadoutProfileDef`

開始、PawnKind、派遣、補給に使う装備生成規則を所有する。

```text
ShionLoadoutProfileDef
├─ exactEntries[]
└─ familyEntries[]
```

`exactEntries`は具体的な`ThingDef`を指定する。候補フィールドは`thingDef`、`stuffDef`または素材規則、品質、数量、配置、所有形態である。

`familyEntries`は具体Thingを選ぶための生成指示である。候補フィールドはFamilyDef、数量、装備ポイント予算、配置、所有形態、多様性方式、失敗方針である。FamilyDef側は役割、装備部位、明示的な候補ThingDefまたはStyle、身体互換、性能・費用帯を持つ。

解決処理:

1. Profileと全参照Defを検証する。
2. 具体エントリのThingを確定する。
3. Familyエントリごとに明示候補を列挙する。
4. Pawnの身体、Family規則、予算に適合しない候補を除く。
5. 固定順、重み付き、重複回避等の選択規則で一件以上の具体Thingを決める。
6. 全エントリの解決成功後にThingを生成し、装着、所持、地上配置、共同倉庫へ分配する。
7. 個人／共同／貸与の由来を必要な範囲で記録する。

開始生成は原子的に扱う。必須エントリの解決失敗時に一部だけ生成して続行しない。解決後は生成されたThingが正本であり、Familyエントリや装備ポイントは所持品として保存しない。由来や生成Profileを診断用に保存しても、ロード時の再抽選には使わない。

`ShionBodyModuleDef`と装備Thingを同じデータで表現しない。身体構成として組み込む拡張はModule、着脱して装着・所持・保管・貸与・喪失する武器、防具、工具はThingである。Familyエントリと装備ポイントはModuleスロットを生成しない。
