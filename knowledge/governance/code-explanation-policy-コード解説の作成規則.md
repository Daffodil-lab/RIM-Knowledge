# コード解説の作成規則

RIMプロジェクトでC#、XML Def、保守スクリプト、生成器、設定、GitHub Actionsなどの動作を変更する場合、事前知識がない人でも変更の仕組みと影響範囲を追える日本語のコード解説を同じPull Requestへ含める。コード解説は検査やコードレビューの代替ではなく、所有者が適切な質問と公開判断を行うための説明を提供する。

## 解説の所有先

Pull Requestは、その変更で何が変わったかを説明する。変更後も有効な仕組み、状態遷移、所有境界、失敗時結果は、対象実装の既存`canonical_for`所有者へ記録する。Pull Requestだけに永続仕様を残さず、同じ事実を新しい解説専用正本へ複製しない。

コードの動作を変えず、整理、改名、書式変更だけを行う場合も、動作説明の更新が不要である理由をPull Requestへ記録する。

## 解説の四層

### 1. 一分要約

- 何のためのコードか。
- 何を入力として、利用者には何が起きるか。
- 今回何が変わり、何を変えないか。

### 2. 動作の流れ

起点から結果までを番号付きで示す。各段階で、入力確認、正本データの読取り、状態変更、出力、副作用、拒否または失敗時の結果を記述する。成功経路だけでなく、対象を変更せず終了する条件と、途中失敗時に維持または復旧される状態を含める。

### 3. コード対応表

| 項目 | 記載内容 |
|---|---|
| ファイル、型、関数 | 安定した識別名と担当する処理 |
| 入力 | 呼出元、引数、読取る設定または正本データ |
| 出力と状態変更 | 戻り値、保存状態、生成物、外部副作用 |
| 失敗時結果 | 拒否条件、例外、ログ、rollback、再試行 |
| 所有境界 | その状態を権威的に所有する型、コンテナ、概念正本 |
| 検査 | 対応する自動試験、build、runtime確認、未確認事項 |

表は重要な入口と状態変更を優先し、構文を一行ずつ言い換えない。コード断片は、文章だけでは条件や順序を誤解しやすい箇所に限定し、直後に日本語で意味を説明する。

### 4. 用語と証拠

略語、型名、RimWorld固有概念を初出時に説明する。実行したコマンド、結果、対象環境、未実施のruntimeまたは手動確認、既知の制限、戻し方を記録する。「検査合格」と「人が動作を確認した」を分離する。

## 生成コードと派生資料

生成物を変更する場合は、生成器、入力、テンプレート、出力先、再生成コマンド、手編集可能な境界を説明する。所有者が生成物の全行を読むことを前提にせず、生成元の変更と生成差分の範囲を示す。派生資料を正本として説明しない。

## コード内コメント

コード内コメントは、処理を見れば分かる構文ではなく、所有境界、成立条件、順序制約、性能上の理由、失敗時保証、外部APIの制約を記述する。長い全体説明は正本またはPull Requestへ置き、コメントから参照できる安定した識別名を使う。

## 更新条件

既存の入力、状態遷移、出力、失敗時結果、依存関係、性能条件、保存互換を変えるPull Requestは、対応するコード解説も同時に更新する。解説とコードが一致しない場合は解説を確認済みとして扱わず、Pull RequestをDraftに維持する。

所有者が次の質問へ日本語で答えられる状態を、解説完了とする。

1. このコードは何を実現するか。
2. 何を読み、どの正本データを変更するか。
3. 成功、拒否、途中失敗で何が起きるか。
4. どこまで検査され、何が未確認か。
5. 問題が起きた場合にどう止め、どう戻すか。
