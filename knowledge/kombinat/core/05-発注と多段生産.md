# 5. 発注と多段生産

αの発注は具体的なThingDef、Recipe、数量または目標在庫を基本とする。

通常プレイヤーは次だけを指定する。

- 何を作るか
- いくつ作るか、またはいくつ維持するか
- 優先度

PlannerはRecipe依存を有界DAGへ展開し、循環、材料不足、設備不足、出力満杯を区別する。世界最適化や全MOD装備の動的Stat最適化を行わない。

## 不足中間品の自動作成

プレイヤーは最終品を要求すればよく、各中間品を個別に発注する必要はない。Plannerは確定前に、依存する各材料を次へ分類する。

- Storageに実在し、未予約で利用可能
- 他用途または本Requestのため予約済み
- 本Requestの子工程として作成予定
- 公開Endpointからの搬入待ち
- Recipe、設備または原料がなく作成不能

同じ中間品を複数工程が要求する場合は必要数を集約し、既存在庫と他Requestの予約を二重計上しない。親Requestを確定すると、不足中間品を親へ属する子工程として一度だけ生成する。

親Requestの取消では、未commitの子工程予約を解放する。既にStorageへCommitした中間品、他Requestが予約した中間品、要求前から存在した在庫を削除しない。

生産は次の境界を守る。

1. Core独自Storageが入力ThingをThing IDと数量で予約する。
2. 同じOperation IDで出力先Storageの容量を予約する。
3. 全入力予約、設備、出力容量予約が揃った時だけBatchを開始する。
4. 工程完了時にStorageが入力消費と出力生成を一つの冪等Commitとして実行する。
5. 中間品と完成品を指定Storageへ直接置き、Output Claimへ結び付ける。
6. 後段工程はStorage上の中間品を新しい工程Operationで予約する。

保管基盤内にあるだけのThingを、Kombinatが予約済みまたは受領済みとみなさない。Core独自基盤が公開契約で原子的予約を保証したThingだけを計画へ算入する。
